## Important findings
1. **Core orchestration behavior is substantially real, not a demo stub.** The reference implementation has working workspace isolation, app-server integration, reconciliation, retry/backoff, stall handling, concurrency limits, tracker adapters, observability API/dashboard, and deterministic cleanup paths.
2. **The official implementation is still explicitly preview/prototype software.** Upstream warns it is for trusted-environment evaluation and recommends a hardened implementation for production.
3. **Current locked dependencies emit active 2026 security advisories**, including HIGH advisories in Bandit, Mint, Phoenix, Plug and Req. Captured to C2 Inbox as #3715 and #3729. Localhost-only dashboard deployment reduces some server exposure but does not remove all client/parser risk.
4. **GitHub adapter requires a GitHub token even for public repositories.** The current ChatGPT execution channel blocks extracting/passing the host `gh` credential into a spawned process, so the external GitHub-adapter E2E was not executed here. Captured as #3707. This is an evaluation-environment blocker, not proof that the adapter is defective.
5. **Model selection pitfall:** `codex -m gpt-5.6-terra app-server` did not set the model used by the app-server thread; the real canary rollout used global `gpt-6-sol` medium. `codex -c model=gpt-5.6-terra -c model_reasoning_effort=medium doctor` confirms the invocation config override selects `gpt-5.6-terra`. Any Symphony workflow must use `-c model=...` / `-c model_reasoning_effort=...`, not `-m`, for app-server. Captured as #3764.
6. **Restart is reconciliation, not durable live-session recovery.** Running sessions, in-memory retry timers, and blocked maps are not persisted across a Symphony process restart; the tracker + preserved workspaces are used to rediscover/re-dispatch. This is acceptable for idempotent coding runs but is weaker than full process-state persistence.

## Recommended architecture

`Inbox / semantic planning / MegaVault / roadmap` remains the global control plane for now. Runnable autonomous coding work is published through a thin **Symphony execution bridge** to a tracker Symphony already supports (prefer GitHub Issues for the pilot to avoid a Symphony fork). Symphony owns Codex workspace/process/retry/reconciliation. ChatGPT Web/Desktop and native-system lanes stay outside Symphony and remain visible to the cross-surface registry.

Do **not** implement a custom `roadmap.sqlite` tracker adapter inside Symphony yet. The reference adapters are compiled into the Elixir implementation, so doing that now would create a local fork and restore the maintenance burden we are trying to remove. A supported-tracker bridge is cheaper to maintain during the pilot.

## Migration decision

**ACQUIRE: PASS.** Keep the upstream checkout and verified release/runtime available for continued pilot work.

**TECHNICAL CANARY: PASS.** Symphony genuinely performs the core Codex orchestration functions C2 currently reimplements.

**IMMEDIATE PRODUCTION CUTOVER: HOLD.** Do not make v0.0.3 the sole engine of C2 yet. The hold is based on the preview/prototype status, current dependency advisories, the untested authenticated GitHub-adapter E2E in this execution environment, and restart semantics that deliberately reconstruct rather than persist live sessions.

**C2 DEVELOPMENT FREEZE:** avoid new work on Codex dispatch, app-server RPC, per-worker retry, stall detection, Codex concurrency, and workspace lifecycle unless required to keep the current system operational during migration. Those areas are intended to be replaced by Symphony.
